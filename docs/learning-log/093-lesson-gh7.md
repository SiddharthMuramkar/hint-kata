It explains what a status check is (a result stuck to a commit, posted by an app such as GitHub Actions, named after the job), why a pull request can sit on "Waiting for status to be reported" (a misspelled or renamed check, a workflow that a `paths:` filter kept from starting), and the three kinds of skip: a skipped workflow leaves its checks pending, a skipped job counts as success even when it is required, and a job that needs a failed job may not block. Things to know about how I built it. GH2's task already makes `checks` required, so step 2 of the task first looks at what `main` requires and only creates a second ruleset (`require-checks`, with exact JSON) if the rule is missing. I could not run that `POST`, because I changed nothing on any repo; the JSON matches the shape of the live ruleset on hint-kata. The task arms auto-merge while the pull request is still blocked and then pushes the fix. If the learner armed it after a fast green check, `gh` would merge at once and leave no auto-merge record. The `--delete-branch` no-op is not in `gh pr merge --help`; I confirmed it in the `gh` v2.102.0 source (`pkg/cmd/pr/merge/merge.go`). The lesson uses only source ids that were already in `content/sources.yaml`, and I added none. The four checks in `task/check.yaml` are read-only `gh` calls: `checks` is required on `main`, auto-merge and delete-branch-on-merge are on, a pull request run failed, and a merged pull request has an auto-merge record (`autoMergeRequest` stays filled on merged pull requests, which I checked on hint-kata). I ran them with `app.checker.run_gh_checks`. All four pass on hint-kata today, none pass on `octocat/Hello-World`, and a repo that does not exist fails all four with the API error shown.

One lesson learned: `gh pr merge --auto` does not always wait. If the pull request can already merge, `gh` merges at once, and the "auto-merge" record never exists. Order matters, so arm auto-merge while the pull request is still blocked.
