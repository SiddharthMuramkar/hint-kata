# RAG and content pipeline tooling

_Research archive. Checked against primary sources on 2026-10-14. Facts about fast-moving tools (Claude Code, Pydantic AI, FastAPI, GitHub, OpenRouter) go stale quickly: re-check before relying on a number._

- **Needed by:** Phase 2 (fetch script is Phase 1)
- **Licence / attribution notes:** Library licences: markdown-it-py MIT, pgvector-python MIT, psycopg LGPL-3.0, semchunk MIT.
- **Covers:** chunking, include resolvers, Article API, pgvector/psycopg, hybrid search SQL, contextual retrieval, re-sync workflow, retrieval evals

## Content pipeline and RAG tooling for a private learning site (Pydantic AI / FastAPI / GitHub tracks): heading-aware Markdown chunking, include and Liquid resolution, pgvector hybrid search on Neon, Contextual Retrieval and reranking, incremental re-sync through GitHub Actions, and retrieval evaluation

**Summary.** You can get all three doc sources as clean Markdown without running any of their doc builds. FastAPI: use a pinned git checkout and expand its `{* path ln[..] hl[..] *}` includes with your own small resolver. Every FastAPI heading already has an explicit `{ #anchor }`, so citation URLs are stable. Pydantic AI: its docs moved to pydantic.dev/docs/ai. The source .md files in the repo have no snippet includes because code is written inline. `docs/navigation.yml` maps each file path to its public URL, and every page is also served as rendered Markdown at `<slug>/index.md`. GitHub Docs: you don't need to render Liquid, because the official Article API (`docs.github.com/api/article/body?pathname=...`) returns fully rendered Markdown. I checked this: zero Liquid tags remained in the output. Don't use the line-based Markdown splitters in LangChain or LlamaIndex: both have recent bugs where code fences are detected wrongly. A small custom splitter on markdown-it-py 4.2.0 is safer and lighter. Use one chunk per heading section, keep code blocks whole, aim for about 300–500 tokens with no overlap, and put the heading path at the front of the text you embed. On Neon, pgvector 0.8.x with psycopg 3.3.6 and pgvector-python 0.5.1 supports async connections, HNSW, halfvec and iterative scans. Hybrid search can be done in one SQL query: `websearch_to_tsquery` for keywords plus vector search, merged with reciprocal rank fusion (k=60). Contextual Retrieval is optional at this size. Start with the heading-path prefix and measure, then try voyage-context-4 or LLM-written context prefixes only if recall is too low. For re-sync, compare content hashes of the expanded Markdown, not git SHAs of the files. Run the sync as a weekly 'plan' PR (diff report plus lockfile) and apply embeddings when it merges. Evaluate retrieval with a small golden set (recall@k and MRR in a custom pydantic-evals Evaluator) and the answers with LLMJudge rubric recipes. Engine note: Tavily answered one search, then failed with HTTP 429 and then 432 (plan usage limit) on both search and extract. So most sources came from Firecrawl, Octen, read-only `gh api`, and curl of the primary sources.

**Engines used:** Firecrawl: firecrawl_developer_search (used 8 times: LangChain and LlamaIndex splitter bugs, chonkie, FastAPI include syntax, GitHub Docs article API, markdown-it-py, semchunk, hybrid RRF SQL, pgvector halfvec, LangChain indexing API), firecrawl_scrape in query mode (Anthropic Contextual Retrieval, Chroma chunking research), firecrawl_research_search_papers (chunk size and overlap papers); Octen: search (markdown-include-variants, voyage-context-4, Vercel limits, incremental re-sync), broad_search (reranker landscape and pricing), extract (GitHub Docs API page, Voyage pricing, Postgres text search docs); Tavily: tavily_search gave 1 result set (Pydantic AI llms.txt and docs location), then failed with HTTP 429 and then 432 'exceeds your plan's set usage limit'; tavily_extract also failed with 432; Read-only gh api (repo contents, trees, issues, releases, code search) and curl (live pages, .md endpoints, GitHub Docs Article API, PyPI JSON) for primary-source checks; Neon MCP list_docs_resources (read-only docs index), then curl of Neon .md docs

### Findings

- **FastAPI's `{* ../../docs_src/... *}` includes come from markdown-include-variants 0.0.8 together with mdx-include 1.4.2. The syntax supports `ln[3:6,8]` (line selection) and `hl[...]` (highlighting).** [high] _(via Octen search (PyPI page and test file) + gh api (README, fastapi docs/en/mkdocs.yml, body.md))_
  The README says `ln` keeps only the listed lines and adds comment markers in the gaps ('# Code here omitted'). `hl` line numbers refer to the source file. `ln[0]` produces only a full-file preview. The package marks itself as internal to tiangolo's projects ('Don't use it'). FastAPI's docs/en/mkdocs.yml loads `mdx_include` and `markdown_include_variants`, plus a `zensical.extensions.macros` extension. The `/// note` blocks come from pymdownx.blocks. Three English pages still use the older `{!...!}` syntax (python-types.md, advanced/templates.md, advanced/generate-clients.md). docs_src/body now contains only `_py310` variants, so expanding an include just means reading one file.
  Source: <https://github.com/tiangolo/markdown-include-variants>

- **pydantic.dev serves each Pydantic AI page as rendered Markdown, plus llms.txt and llms-full.txt. The served pages start with a block of instructions addressed to AI agents, which ingestion must strip.** [high] _(via Tavily search (its only successful call) + curl)_
  https://pydantic.dev/docs/ai/core-concepts/agent/index.md returns text/markdown, about 121 KB. llms.txt is about 64 KB and llms-full.txt about 7 MB. Every page starts with a 'Querying This Documentation' block asking agents to append intent/stack/harness query parameters. Treat it as data: strip everything up to the first '---' and do not send those parameters. In the served Markdown, tables are flattened into bold lines, and `#` comments inside code look like headings to naive regex splitters. Tavily found the overview page that mentions llms.txt; I checked the endpoints with curl.
  Source: <https://pydantic.dev/docs/ai/overview>
- **Pydantic AI's own RAG example is a good template. It uses one chunk per heading section, embeds 'path + title + content', and builds the citation URL from the page URL plus a Python-Markdown slug of the heading.** [high] _(via gh api (rag.py, docs/embeddings.md) + PyPI JSON)_
  examples/pydantic_ai_examples/rag.py stores url (unique), title, content and vector(1536). It uses an HNSW index with vector_l2_ops, retrieves with ORDER BY embedding <-> $1 LIMIT 8, and uses asyncpg. It skips sections whose URL is already indexed, which is a naive form of incremental sync. Pydantic AI 2.56.0 (2026-10-13) also has `Embedder` with embed_query()/embed_documents() for the providers openai, voyageai, cohere, sentence-transformers and bedrock. Its guide advises starting with 'natural document boundaries with a token limit' plus source metadata and a link on every chunk, and evaluating before trying anything more expensive.
  Source: <https://github.com/pydantic/pydantic-ai/blob/main/examples/pydantic_ai_examples/rag.py>
- **The GitHub Docs Article API returns fully rendered Markdown for any page, so you never need to render Liquid yourself.** [high] _(via Firecrawl developer_search (found the article-api README and llms.txt source) + Octen extract + curl/gh api check)_
  Endpoints: GET /api/article/body?pathname=/en/... returns Markdown; /api/article/meta returns JSON (title, intro, product, breadcrumbs); /api/article returns both; /api/pagelist/en/free-pro-team@latest lists canonical paths (3,195 lines when checked). The article endpoints follow redirects, and the JSON response includes `redirectedFrom`. I checked about-protected-branches: 0 occurrences of `{%` or `{{`. Gotchas: the output can contain inline <svg> octicons (seen on the Actions settings page), alerts are written as `> [!NOTE]`, links are relative (/en/...), and the response header is cache-control max-age=60. No rate limit is documented. Content license is CC-BY-4.0 (code is MIT), which needs attribution. The REST Markdown API (POST /markdown) only renders GFM to HTML and would not resolve the docs site's Liquid (my inference).
  Source: <https://docs.github.com/en/get-started/using-github-docs/github-docs-api>
- **The Claude Code docs, useful for track 3, are also available as Markdown.** [high] _(via curl)_
  https://code.claude.com/docs/llms.txt (about 62 KB) and per-page .md files, e.g. https://code.claude.com/docs/en/github-actions.md (text/markdown). These pages start with a short 'Documentation Index' preamble to strip.
  Source: <https://code.claude.com/docs/en/github-actions.md>
- **The line-based Markdown header splitters in LangChain and LlamaIndex keep shipping code-fence bugs, which matter for code-heavy technical docs.** [high] _(via Firecrawl developer_search + gh api (issue state) + PyPI JSON)_
  LangChain MarkdownHeaderTextSplitter: #41061 closes a fence on a shorter or info-string fence, so `#` lines inside code become headers (closed 2026-10-05). #40071 strips tabs and indentation inside fenced code (still open). LlamaIndex MarkdownNodeParser: #23282 closes a code block on a shorter backtick fence (open, 2026-09-28); #17599 gives a wrong header_path when heading levels jump; #17965 uses '/' as the path separator. Dependency weight: langchain-text-splitters 1.1.3 needs langchain-core; llama-index-core 0.14.25 has 29 core dependencies.
  Source: <https://github.com/langchain-ai/langchain/issues/41061>
- **markdown-it-py 4.2.0 (one dependency, mdurl) plus mdit-py-plugins 0.6.1 is the lightest correct base for a custom heading-aware splitter.** [medium] _(via Firecrawl developer_search + PyPI JSON)_
  It parses CommonMark into a token stream: heading_open tokens, fence tokens carrying `info` (the language), and block tokens carrying `map` (source line ranges). From that you can cut sections at heading boundaries, keep fences whole, and keep a stack of heading text for breadcrumbs. mdit-py-plugins includes an anchors plugin (custom slug_func), and the attrs plugins can help with `{#id}`; a regex on the trailing `{ #id }` also works. extract_thinker's MarkdownSplitter shows the same approach: built on markdown-it-py, headings inside code fences are left intact, and line ranges are kept.
  Source: <https://github.com/executablebooks/markdown-it-py/blob/master/docs/using.md>
- **chonkie 1.7.0 and semchunk 4.1.1 are maintained but solve different problems: chonkie pulls code apart from prose, while semchunk is a tiny size limiter.** [medium] _(via Firecrawl developer_search + gh api + PyPI JSON)_
  chonkie (MIT, about 4.8k stars, 6 core deps including numpy>=2, chonkie-core, tokie, httpx): MarkdownChef uses regexes to extract tables, code and images into a MarkdownDocument. Its pipelines chunk prose with RecursiveChunker and code blocks separately with CodeChunker, which detaches example code from the text that explains it. semchunk (deps: tqdm only): a recursive, token-aware splitter with `overlap` and character `offsets` that works with tiktoken or HF tokenizers. Good for splitting an oversized prose section inside a heading section.
  Source: <https://docs.chonkie.ai/oss/chefs/markdownchef>
- **Published evidence supports small to medium chunks with no overlap.** [high] _(via Firecrawl scrape (query mode) + Firecrawl research_search_papers)_
  Chroma's chunking evaluation, RecursiveCharacterTextSplitter: 200 tokens / no overlap was consistently strong (recall 88.1, IoU 7.0). 400/0 had recall 89.5. The OpenAI default of 800/400 had the worst efficiency (IoU 1.5). Reducing overlap improves IoU. arXiv 2601.14123 (2026) found overlap gives no measurable benefit and adds indexing cost, and sentence chunking matches semantic chunking up to 5k tokens of context. arXiv 2505.21700 found 64–128 tokens best for short factual answers and 512–1024 for questions that need broader context.
  Source: <https://research.trychroma.com/evaluating-chunking>
- **pgvector-python 0.5.1 (2026-10-09) supports psycopg 3.3.6 sync, async and pooled connections, and halfvec.** [high] _(via gh api (README) + curl of Neon docs (connection-pooling.md, found via the Neon MCP docs index))_
  Call `register_vector(conn)` (sync), `await register_vector_async(conn)` (async), or `ConnectionPool(..., configure=...)` (pool). Vector, HalfVector, Bit and SparseVector are supported, and SQLAlchemy has HALFVEC. Neon's pooled endpoint is PgBouncer in transaction mode: session-level SET, temp tables and SQL PREPARE are not supported, but protocol-level prepared statements are (max_prepared_statements=1000). So set hnsw.ef_search with SET LOCAL inside a transaction, or with ALTER ROLE/DATABASE ... SET.
  Source: <https://github.com/pgvector/pgvector-python#psycopg-3>
- **HNSW and halfvec facts for pgvector, and the versions Neon ships.** [high] _(via gh api (pgvector README and tags) + curl of Neon pg-extensions.md)_
  Defaults are m=16, ef_construction=64 and hnsw.ef_search=40; higher values give better recall but slower queries or builds. Maximum indexable dimensions: vector 2,000 and halfvec 4,000. A half-precision expression index looks like `USING hnsw ((embedding::halfvec(N)) halfvec_cosine_ops)`, and the query must use the same cast. Iterative scans (0.8.0+) fix filtered queries that return too few rows: `hnsw.iterative_scan = relaxed_order`, with hnsw.max_scan_tuples default 20000. Builds are faster when maintenance_work_mem holds the graph. Neon ships pgvector 0.8.0 on PG14–17 and 0.8.6 on PG18; the upstream latest tag is v0.8.7.
  Source: <https://github.com/pgvector/pgvector#hnsw>
- **Hybrid search can be one SQL statement: a full-text CTE and a vector CTE, each ranked with RANK(), joined with FULL OUTER JOIN, and scored by reciprocal rank fusion.** [high] _(via gh api + Octen extract (Postgres textsearch-controls) + Firecrawl developer_search (DocsGPT PR) + curl of Neon lakebase-search-get-started.md)_
  pgvector-python examples/hybrid_search/rrf.py: each CTE takes LIMIT 20 with RANK() OVER (...); score = COALESCE(1.0/(k+semantic.rank),0) + COALESCE(1.0/(k+keyword.rank),0) with k=60; keyword search uses a GIN index on to_tsvector('english', content) and ts_rank_cd. Neon's guide uses 40 candidates per list, k=60, and breaks ties by id. Use websearch_to_tsquery instead of plainto_tsquery: it accepts unformatted text and also understands quotes, OR and '-'. Projects such as DocsGPT use exactly this (websearch_to_tsquery + RRF k=60).
  Source: <https://github.com/pgvector/pgvector-python/blob/master/examples/hybrid_search/rrf.py>
- **Neon now offers 'Lakebase Search' extensions for BM25 and IVF-based vector search; pg_search is unavailable and pgrag is deprecated.** [high] _(via curl of Neon docs .md (index from Neon MCP list_docs_resources))_
  lakebase_text 0.1.3 adds a BM25 index (lakebase_bm25) and works with standard tsvector. lakebase_vector 1.1.1 adds lakebase_ann (IVF + RaBitQ, stored in storage so it survives scale-to-zero). Both need PG16+. There is no built-in hybrid function; Neon's guide writes the RRF by hand. At about 10k chunks, plain tsvector + GIN with pgvector HNSW (or even exact search) is enough.
  Source: <https://neon.com/docs/ai/lakebase-search>
- **Anthropic's Contextual Retrieval: in Anthropic's tests, adding context to each chunk cut retrieval failures by 35% (embeddings only), 49% (with contextual BM25) and 67% (with reranking). Anthropic also says a knowledge base under 200k tokens can simply go in the prompt.** [high] _(via Firecrawl scrape (query mode) + gh api tree sizes)_
  Measured as 1 − recall@20: 5.7% → 3.7% → 2.9% → 1.9%. Cost was $1.02 per million document tokens with prompt caching, assuming 800-token chunks, 8k-token docs, 50-token instructions and 100 tokens of context per chunk; context added is usually 50–100 tokens. They pass the top 20 chunks and used a Cohere reranker. Here the whole corpus is about 1M+ tokens (Pydantic AI non-API docs about 3.7 MB, FastAPI without release notes about 0.78 MB), so global RAG makes sense. But the source pages of a single lesson (roughly 5–30k tokens) could go straight into the tutor's prompt.
  Source: <https://www.anthropic.com/engineering/contextual-retrieval>
- **voyage-context-4 adds document context to each chunk embedding without generating any LLM prefixes, which makes it a cheap alternative to Contextual Retrieval.** [medium] _(via Octen search + Octen extract (pricing))_
  You call contextualized_embed(inputs=[[chunks of doc 1], ...], input_type='document'); auto-chunking is optional. Matryoshka dimensions are 2048/1024/512/256 and the per-chunk context is 32k tokens. Queries are sent as single-item lists. Voyage recommends chunks without overlap. The voyage-context-3 blog claims it beats Anthropic-style contextual retrieval and Jina late chunking on Voyage's own benchmarks; these are vendor claims, not independently checked. The first 200M tokens are free for the voyage-4 family and voyage-context-4.
  Source: <https://docs.voyageai.com/docs/contextualized-chunk-embeddings>
- **Reranking is cheap by API; local cross-encoders are a poor fit for Vercel.** [medium] _(via Octen broad_search + Octen extract + Octen search (Vercel limits) + PyPI JSON)_
  Voyage rerank-3 costs $0.05 per 1M tokens and rerank-3-lite $0.02 per 1M. The first 200M tokens are free for rerank-2.5 and 2.5-lite according to the extracted page text, and the price table also lists 200M free for rerank-3 and 3-lite. Billed tokens are (query tokens × number of docs) + doc tokens, with 32k context. Cohere Rerank 4 (Pro and Fast, announced Dec 2025) also has 32k context. Running a cross-encoder locally needs sentence-transformers 6.1.0, which pulls in torch>=2.2 and transformers 5. Vercel's bundle limit is 250 MB unzipped (500 MB for Python; a 'large functions' beta allows more), so torch would be heavy there.
  Source: <https://docs.voyageai.com/docs/pricing>
- **Scheduled GitHub Actions have limits that matter for a docs re-sync job, and pull requests opened with GITHUB_TOKEN do not trigger CI.** [high] _(via curl via the GitHub Docs Article API + gh api (create-pull-request docs and releases))_
  Schedule facts: workflows run only on the default branch; they can be delayed, or queued jobs dropped, under load, especially at the start of each hour; in public repos they are disabled after 60 days without activity; the minimum interval is 5 minutes; an IANA timezone is now supported. peter-evans/create-pull-request is at v8.1.1 (2026-04-10). Its docs say PRs created with the default GITHUB_TOKEN do not trigger on: pull_request or push workflows, so use a GitHub App token or a PAT. The repository setting 'Allow GitHub Actions to create and approve pull requests' must be on. Current action versions: actions/checkout v7.0.1, setup-python v7.0.0, astral-sh/setup-uv v10.3.0.
  Source: <https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule>
- **Detect changes by hashing the rendered or expanded content, not by git file SHAs.** [medium] _(via Firecrawl developer_search + Octen search)_
  A FastAPI page changes when an included docs_src/*.py file changes, even if its .md does not. A GitHub Docs page changes through reusables without its own file changing, and the Article API gives you no SHA at all. Common pattern (e.g. the LangChain indexing API with RecordManager): hash content per source id, skip unchanged items, and in 'incremental' mode delete stale chunks for every source seen in the run. Open LangChain issue #40334 asks for metadata-only updates without re-embedding. Keeping chunk identity (citation key) separate from the content hash makes both possible.
  Source: <https://reference.langchain.com/python/langchain-core/indexing/api/index>
- **pydantic-evals 2.56.0 has no built-in recall@k or MRR, but a custom Evaluator returning a float is trivial. It ships LLMJudge rubric recipes for RAG.** [high] _(via gh api (docs/evals/evaluators/*.md, navigation.yml) + PyPI JSON)_
  To define an evaluator, subclass Evaluator and implement evaluate(ctx) -> bool | float | dict. Datasets of Cases can be saved to and loaded from YAML or JSON. The 'Standard Quality Metrics' page gives ready-made LLMJudge rubrics for faithfulness, answer relevance, context precision and context recall (judged on supplied context), plus G-Eval. Report evaluators include PrecisionRecallEvaluator, ROCAUC and ConfusionMatrix. Dependencies: pydantic-ai-slim, logfire-api, pyyaml, rich, anyio.
  Source: <https://pydantic.dev/docs/ai/evals/evaluators/standard-quality-metrics/>
- **Heading anchors differ between renderers, so a citation URL is only stable if it uses explicit ids or the same slug function the site uses.** [high] _(via curl (live HTML ids) + gh api)_
  FastAPI writes explicit `{ #id }` on every heading. Pydantic AI uses explicit `{#id}` on some headings and generated slugs on the rest; I confirmed ids like running-agents on the live page. Pydantic's RAG example copies Python-Markdown's toc slugify. GitHub Docs uses GitHub-style slugs. Cheap safeguard: a CI step that fetches each cited page's HTML and checks that the `id="..."` exists.
  Source: <https://pydantic.dev/docs/ai/core-concepts/agent/>

### Recommendations
- Sources and pinning. FastAPI: shallow clone at a release tag (currently 0.143.0) and ingest docs/en/docs/**/*.md. Exclude release-notes.md, or index it separately with lower weight. Pydantic AI: pin a release tag (currently v2.56.0), ingest docs/**/*.md, and map URLs through docs/navigation.yml; you can fall back to fetching the served `<slug>/index.md` after stripping the preamble. GitHub: a curated list of roughly 60–120 pathnames (protected branches, rulesets, status checks, PR reviews and merging, workflow syntax, GITHUB_TOKEN permissions), fetched from the Article API with a polite rate (about 1 request/s) and a User-Agent header. Claude Code: the .md endpoints. Record every source in a committed sources.lock.json: repo tag and commit SHA, or for API pages the pathname, fetched_at and body sha256.
- FastAPI include resolver. Write your own small resolver instead of importing markdown-include-variants, which says it is internal and not for outside use. Regex for `{* <path> [ln[...]] [hl[...]] *}` and `{!<path>!}`. Resolve paths relative to the .md file. Apply `ln` ranges with a '# Code omitted' line in each gap, drop `hl`, and wrap the result in a python fence. Turn `/// note | Title` … `///` blocks into blockquotes, and strip the heading `{ #id }` after reading it as the anchor. Add a CI assertion that no `{*` or `{!` remains after expansion.
- Pydantic AI normaliser. Convert `!!! note "x"` and `??? ` blocks into blockquotes. Rewrite autorefs `[text][pydantic_ai.mod.Name]` to plain `text`, or link them to the API page. Remove fence attributes like `{title=... requires=...}` but keep the title as a 'File: x.py' caption. Keep `#>` output lines because they are useful to learners. Anchor = explicit `{#id}`, otherwise a GitHub-style slug; verify it against live HTML in CI.
- Chunker. Build a custom splitter on markdown-it-py 4.2.0, mdit-py-plugins 0.6.1 and tiktoken 0.14.0 (or your embedding provider's tokenizer). Unit = a heading section (H2/H3) with its heading stack and anchor. Target 300–500 tokens, hard maximum about 800, overlap 0. Never split inside a fence; a fence up to about 1,500 tokens stays whole. Split oversized prose at paragraph or list boundaries, using semchunk 4.1.1 only for prose. Merge sections under about 80 tokens into the next sibling. Embedded text = 'Track › Page title › H2 › H3' + blank line + chunk (the same cheap contextualisation as Pydantic's RAG example); store the display text separately. Don't use the LangChain or LlamaIndex Markdown splitters because of their open fence bugs.
- Schema on Neon (prefer a PG17 or PG18 project; PG18 gets pgvector 0.8.6). Table `pages(source, path, url, title, version_ref, content_sha256)`. Table `chunks(chunk_key PK, page_id, anchor, heading_path text[], ordinal, text, embed_text, content_sha256, embedding_model, embedding vector(N), tsv tsvector GENERATED from setweight(heading_path,'A') || setweight(text,'B'))`. chunk_key = sha256(source|page path|anchor|ordinal within section), so it stays stable across edits; content_sha256 = sha256(embed_text + model id). Indexes: GIN on tsv; HNSW on embedding with vector_cosine_ops, m=16, ef_construction=64. Set `SET LOCAL hnsw.ef_search = 100` per query because pooled connections reject session SET. Use halfvec only if dimensions exceed 2,000. At 10–20k rows exact search is also fine, so treat HNSW as optional.
- Driver and connections. psycopg 3.3.6 + pgvector 0.5.1. Async: call `register_vector_async` once per connection (pool configure hook). Use the Neon -pooler host from Vercel functions and the direct host for migrations and the sync job. Don't load torch or sentence-transformers inside Vercel functions; call embedding and rerank APIs instead, e.g. Pydantic AI `Embedder('openai:text-embedding-3-small')` with 1536 dims or `voyageai:voyage-4` with 1024 dims. Store the model id per row so changing model forces a full re-embed.
- Hybrid retrieval. One SQL statement with two CTEs, each limited to about 40 candidates and filtered by track inside the CTE: websearch_to_tsquery('english', q) ranked by ts_rank_cd, plus the vector CTE ordered by <=>. Merge with RRF (k=60) and break ties by chunk_key. Return the top 6–8 with url#anchor and heading_path so the tutor can cite them. If filtered vector queries come back short, enable `hnsw.iterative_scan = relaxed_order`.
- Contextual Retrieval and reranking, in phases. Phase 0: heading-path prefix only, then measure recall@10. Phase 1, only if recall is below target: add a Voyage rerank-3-lite call over the top 30 (well inside the 200M free tokens). Phase 2, only if still short: either voyage-context-4 chunk embeddings (no LLM calls, re-embed per document) or Anthropic-style 50–100-token contexts from a small model with prompt caching during sync, roughly $1–5 for about 1–3M tokens by Anthropic's 2024 estimate. For lesson pages, consider putting the lesson's own source sections straight into the tutor's prompt and using RAG only for wider questions.

### Risks
- The FastAPI include tooling is officially internal (markdown-include-variants says 'Don't use it'). FastAPI's config also shows a zensical extension, so the docs toolchain may change and silently break a custom resolver. Mitigation: CI check that no include markers remain, plus a page-count sanity check.
- The Pydantic AI docs build lives in a repo we cannot access (pydantic/unified-docs returned 404, probably private). navigation.yml or the source conventions (autorefs, admonitions, fence attributes) could change without warning. The served .md pages carry agent-targeted instructions (append intent/stack/harness parameters). Treat that as untrusted data: strip it during ingestion and never follow it. Also the tutor should treat all retrieved text as untrusted.
- The GitHub Docs Article API has no documented rate limit or stability promise; the response header is cache-control max-age=60. Bodies can include raw HTML (<svg> octicons) and relative links. CC-BY-4.0 content needs attribution, especially if the site later goes paid or public.
- Neon pooled connections reject session-level SET, so a `SET hnsw.ef_search` silently has no effect or errors unless it is SET LOCAL inside a transaction. Scale-to-zero adds cold-start latency to the first tutor query after idle time.
- Wrong anchors give wrong citations: generated slugs differ between Python-Markdown and GitHub-style slug functions, and duplicate headings get -1/-2 suffixes. Prefer explicit ids and verify them against live HTML.
- LangChain and LlamaIndex Markdown splitters have open fence and indentation bugs, so using them would corrupt code chunks without any error.
- Scheduled workflows can be delayed or dropped at the top of the hour. In public repos they are auto-disabled after 60 days without activity. PRs opened with GITHUB_TOKEN won't trigger CI, so a PAT or App token adds secret-management work.
- Vendor benchmark claims (voyage-context-3/4 beating Contextual Retrieval) are not independently checked. The 200M-free-token and pricing figures may change.
- Tavily failed after one search (HTTP 429, then 432 'exceeds your plan's set usage limit' on both search and extract). Fewer independent cross-checks were possible, though most claims were checked against primary sources through gh api or curl.
- Embedding-model or dimension changes force a full re-embed and an index rebuild. Store the model id per row and treat a model change as a migration.
