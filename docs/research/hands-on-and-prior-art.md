_Research archive. Checked against primary sources on 2026-10-14. Facts about fast-moving tools (Claude Code, Pydantic AI, FastAPI, GitHub, OpenRouter) go stale quickly: re-check before relying on a number._

- **Needed by:** Phase 1
- **Licence / attribution notes:** GitHub Skills exercise-toolkit: MIT. learngitbranching: MIT.
- **Covers:** GitHub Skills pattern, Exercism/Boot.dev CLIs, Pyodide status, Codespaces quotas, check-runs API, recommended checker per track

## How interactive developer courses check hands-on tasks, and which task-delivery approach to use per track (Pydantic AI, FastAPI, GitHub) in release 1 of a private learning site, given a Mac with limited RAM

**Summary.** GitHub Skills is still the clearest model for checking GitHub work. Each exercise is an MIT-licensed template repo with one Actions workflow per step. A start workflow opens an "exercise issue". Each step workflow fires on a real GitHub event (push, pull_request, review_requested), checks the work, edits an issue comment with a pass/fail table, then runs `gh workflow enable` to switch on the next step. skills.github.com now redirects to learn.github.com/skills. The other prior art splits into three patterns: local CLI plus tests (Exercism uses `download`/pytest/`submit`; Boot.dev uses `bootdev run`/`submit`), fully in-browser runners (learngitbranching is MIT and 100% client-side; Scrimba records editor events and replays them so you can edit code inside the video), and tutors that hint before answering (CS50 duck, Boot.dev's Boots). Research shows prompt-only guardrails leak answers and that over-strict tutors push learners to other AI tools. In-browser Python is now realistic for Pydantic AI: Pyodide 314.0.7 ships pydantic 2.12.5, fastapi 0.136.1, starlette, httpx, pytest and pytest-asyncio. Pydantic runs its own Pyodide playground for pydantic-ai at play.pydantic.work, with Run and Pytest buttons. pydantic-ai-slim 2.56.0 (released 2026-10-13) includes a Pyodide import fix, and sync tools already run inline on Pyodide. But Pyodide cannot start threads, and FastAPI's TestClient runs through an anyio blocking portal that starts one, so standard FastAPI tests will not run in the browser. Codespaces includes 120 core-hours plus 15 GB-month on GitHub Free and 180 plus 20 GB-month on Pro. The smallest machine is 2 cores and 8 GB RAM and burns 2 core-hours per hour, so Free gives about 60 hours a month. Branch protection on a private repo needs GitHub Pro, and Actions minutes are free only on public repos. So the GitHub track's practice repo should be public. Recommendation for release 1: local practice repo plus pytest through a small CLI for Pydantic AI (using TestModel, no API key) and for FastAPI (using TestClient); a GitHub-Skills-style public practice repo whose checks the site reads through the check-runs API for the GitHub track; in-browser Pyodide only for small Pydantic AI warm-ups; paste-your-output only for steps that need a real LLM or a local Claude Code session.

**Engines used:** Firecrawl: firecrawl_scrape (skills.github.com/learn.github.com, pydantic.run, GitHub protected-branches docs, Exercism Python tests, Pydantic AI testing guide), firecrawl_search (CS50 duck paper, Codespaces machine/idle docs, JupyterLite), firecrawl_developer_search (pydantic-ai on Pyodide, Starlette TestClient/anyio/Pyodide threading), firecrawl_research_search_papers (hint-first tutor RCTs, Bastani PNAS). firecrawl_research_read_paper was loaded but not needed.; Tavily: tavily_search (Codespaces/Actions quotas, DeepLearning.AI Pydantic course, FastAPI async tests/Pyodide FAQ), tavily_extract (learnGitBranching README, Exercism working-locally). Later calls failed: tavily_extract returned HTTP 429 (rate limited) and tavily_search returned HTTP 432 (plan usage limit exceeded).; Octen: search (Pyodide package list, Boot.dev Boots, Pyodide memory), broad_search (Boot.dev/Scrimba patterns, Pydantic learning resources incl. pydantic.run/events/Real Python), extract (full Pyodide package table, play.pydantic.work and its llms.txt, GitHub check-runs REST docs).; gh api (read-only): skills/introduction-to-github (metadata, README, workflow YAML), skills/exercise-toolkit, skills/review-pull-requests, licenses for pcottle/learnGitBranching, exercism/cli, exercism/python, bootdotdev/bootdev, pydantic/pydantic-ai, fastapi/fastapi, pydantic/pydantic.run; pydantic-ai issues/PRs #6086, #6088, #8673, #10134 and release v2.56.0 notes; live check-runs read on skills/introduction-to-github.; curl (read-only): PyPI JSON API for pydantic-ai-slim (requires_dist, release dates).

- **GitHub Skills has moved: skills.github.com redirects to learn.github.com/skills. - **Current GitHub Skills format: the exercise is a template repo (is_template=true, MIT). A 'Copy Exercise' link creates a public copy. Step 0 runs on push to main, creates an exercise issue through a shared reusable workflow, posts Step 1 instructions as an issue comment, then runs `gh workflow enable "Step 1"`.** [high] _(via gh api (read-only repos/skills/introduction-to-github, README, workflow contents))_
  The copy link is github.com/new?template_owner=skills&template_name=introduction-to-github&...&visibility=public. The README says public is recommended 'since private repositories will use Actions minutes'. Step 0 uses skills/exercise-toolkit/.github/workflows/start-exercise.yml@v0.8.1 with permissions contents/actions/issues: write. Every job is guarded by `!github.event.repository.is_template`, so nothing runs in the template itself.
  Source: <https://github.com/skills/introduction-to-github/blob/main/.github/workflows/0-start-exercise.yml>
- **Each step workflow checks the learner's real GitHub action and reports back in the issue. Example: Step 3 runs on pull_request (opened/synchronize/reopened/edited) into main from head_ref 'my-first-branch'. It checks the PR title for a keyphrase and that the PR body is not empty, replaces the last issue comment with a pass/fail results table, fails the job if any check failed, and otherwise posts the next step and enables the next workflow.** [high] _(via gh api)_
  Tools used: peter-evans/find-comment@v3, GrantBirki/comment@v2.1.1 (edit-mode: replace, templated vars), skills/action-keyphrase-checker@v1, and exercise-toolkit markdown templates (checking-work.md, step-results-table.md, watching-for-progress.md). Each check step is marked continue-on-error, and a final step runs `exit 1` if any step outcome was 'failure'. That gives a red/green Actions status the site can read.
  Source: <https://github.com/skills/introduction-to-github/blob/main/.github/workflows/3-open-a-pull-request.yml>
- **skills/exercise-toolkit is MIT-licensed and versioned (tags v0.7.0 to v0.9.1 are in use). Some steps advance on the event alone, without deep checks: in 'Review pull requests', Step 2 fires on pull_request types assigned/review_requested.** [high] _(via gh api)_
  The toolkit holds reusable workflows (find-exercise-issue.yml, start-exercise.yml), actions and markdown templates. review-pull-requests is also an MIT template (pushed 2026-03-31) with workflows 0-start-exercise.yml plus 1-step.yml through 5-step.yml. MIT allows copying the pattern into your own practice repo as long as the license notice is kept.
  Source: <https://github.com/skills/exercise-toolkit>
- **The site can read a practice repo's check results with GET /repos/{owner}/{repo}/commits/{ref}/check-runs. A fine-grained token only needs the 'Checks' repository permission (read). Writing checks through the REST API is limited to GitHub Apps, which are not needed for reading.** [high] _(via Octen (extract) + gh api live demo)_
  ref can be a SHA, branch or tag. A live read-only call on skills/introduction-to-github returned total_count=12 with name/status/conclusion/html_url per run. Pushes to a branch in a fork are not detected, so learners should branch inside the practice repo rather than fork it.
  Source: <https://docs.github.com/en/rest/checks/runs?apiVersion=2022-11-28>
- **Branch protection works on public repos with GitHub Free, but private repos need GitHub Pro, Team or Enterprise. Required status checks and required approving reviews are both branch-protection settings.** [high] _(via Firecrawl (firecrawl_scrape, query format))_
  Quoted from the docs: 'Protected branches are available in public repositories with GitHub Free and GitHub Free for organizations. Protected branches are also available in public and private repositories with GitHub Pro, GitHub Team...' This matters for the lessons on branch protection and 'is this PR ready to merge'.
  Source: <https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches>
- **GitHub Actions is free for standard GitHub-hosted runners on public repos. Private repos get 2,000 minutes a month on GitHub Free and 3,000 on Pro.** [high] _(via Tavily (tavily_search))_
  The plans page also lists Pro's extras for private repos: required reviewers, protected branches, code owners. Actions storage is 500 MB on Free and 1 GB on Pro.
  Source: <https://docs.github.com/en/billing/reference/product-usage-included>
- **Codespaces included quota for personal accounts: GitHub Free gets 120 core-hours and 15 GB-month of storage; GitHub Pro gets 180 core-hours and 20 GB-month. Organization plans get none.** [high] _(via Tavily (billing and plan pages) + Firecrawl (what-are-codespaces and idle-timeout pages))_
  Compute is billed per core-hour: a 2-core machine burns 2 per hour, so Free is about 60 hours of 2-core use and Pro about 90. Overage is $0.18/hr for 2-core and $0.07 per GB-month. The smallest machine is 2 cores, 8 GB RAM, 32 GB disk. Default idle timeout is 30 minutes. Stopped codespaces are deleted after a retention period you set, up to 30 days. Verified students get the Pro-level amounts.
  Source: <https://docs.github.com/billing/managing-billing-for-github-codespaces/about-billing-for-github-codespaces>
- **learngitbranching.js.org is MIT-licensed, actively maintained, fully client-side, and can be pointed at specific setups by URL. That makes it easy to link or embed for git concepts.** [high] _(via Tavily (tavily_extract) + gh api (license/README))_
  Pushed 2026-10-13, about 34k stars. It has a sandbox mode, level series, and `git fakeCreateRemote` for simulated remotes. `?NODEMO&command=...` preloads commands. `build level` exports a level as JSON, `import level` loads one, and `?gist_level_id=<id>` loads a custom level from a gist. The README says there is no backend database or AJAX; the production site is static HTML, JS and CSS.
  Source: <https://github.com/pcottle/learnGitBranching>
- **Exercism's model: a CLI downloads each exercise (README.md, HELP.md, optional HINTS.md, stub file and test file). The learner runs the tests locally with pytest, then `exercism submit` uploads the solution. The Python track runs the same tests on the website.** [high] _(via Firecrawl (scrape) + Tavily (working-locally page) + gh api (licenses))_
  Command: `python3 -m pytest -o markers=task <exercise_test.py>`. The docs recommend `-x --ff` for fast loops. The CLI and the Python track are both MIT. A HINTS.md file per exercise is a cheap way to do hints before answers.
  Source: <https://exercism.org/docs/tracks/python/tests>

Lessons with HTTP tests can target a local server through `bootdev config base_url`. Around this sits game-style motivation (XP, levels, quests, streaks, achievements) and Boots, a Socratic AI tutor.** [high] _(via Octen (broad_search + search on boot.dev and the blog post https://boot.dev/blog/news/introducing-boots-ai-code-explainer) + gh api (license))_
  The CLI detects the current lesson from course progress. Boot.dev says Boots has the full context of the task, what the learner is struggling with, and the instructor's solution, and 'doesn't just hand over the answers'. Its own advice is to ask Boots before peeking at the solution. This is a close template for the site's tutor plus a `learn check` CLI.
  Source: <https://github.com/bootdotdev/bootdev>
- **Scrimba's 'scrims' record editor and DOM events rather than pixels and replay them, so the learner can pause the 'video' and edit and run the instructor's code in place. Scrimba now also offers 'Explain', an MCP plugin for Claude Code and Codex that turns a question into a narrated video walkthrough.** [medium] _(via Octen (broad_search; also https://hashnode.com/forums/thread/how-does-scrimbas-inline-code-editor-cum-video-viewer-work/comment/590b0773ef8481a8c7ed5a03 and https://bestofshowhn.com/yc-s20/scrimba))_
  The event-replay explanation comes from a Scrimba team forum answer and their YC launch post. The Explain plugin is free during open beta (per a Scrimba article dated 2026-08-18). The idea worth copying is to make the reading itself runnable and editable.
  Source: <https://scrimba.com/articles/how-to-use-scrimba-explain/>
- **The CS50 Duck (CS50.ai) relays student questions to GPT-4o with system-prompt guardrails meant to give leading questions, not solutions. Its authors report that prompts alone were not reliable: the duck sometimes produced long code blocks despite instructions. They moved to evaluation-driven refinement (few-shot prompting, fine-tuning, head-to-head comparisons scored with Elo ratings).** [medium] _(via Firecrawl (firecrawl_search))_
  The paper names 'instruction dilution' as a failure mode. One prompt variant: 'do not diagnose errors or provide future steps, but rather provide some encouragement and ask them leading questions or hints'. For the site: test the tutor's hint behaviour against a small evaluation set rather than trusting the prompt.
  Source: <https://cs.harvard.edu/malan/publications/fp0627-liu.pdf>
- **Research supports hint-first tutors but warns against over-strict ones. Bastani et al. (PNAS 2025) found an unguarded GPT tutor helped during practice but hurt later unaided performance, and a guardrailed version avoided that. A 2026 controlled trial (arXiv 2609.29995) found a Socratic tutor with full context was rated least supportive. In another study, 50% of 885 students used a 'See Solution' escape hatch at least once (arXiv 2504.11146).** [medium] _(via Firecrawl (firecrawl_research_search_papers; also https://arxiv.org/abs/2609.29995, https://arxiv.org/abs/2504.11146, https://arxiv.org/abs/2608.12292))_
  arXiv 2608.12292 describes enforcing answer-withholding as a per-turn contract: a non-LLM policy sets a ceiling on an eight-rung help ladder, a detector strips solution code, and an LLM judge checks risky replies. For the site: use a visible hint ladder (nudge, concept, pointer to the docs section, partial code, full answer) with an explicit, logged 'reveal' button rather than a hard refusal.
  Source: <https://doi.org/10.1073/pnas.2422633122>

  Its llms.txt documents a mirror of Emscripten wheels (e.g. jiter), a wheel builder for branch SHAs, and a proxy covering openai, anthropic, gemini, groq, mistral, cohere, openrouter and xai (keys forwarded, not stored). - **Pyodide 314.0.7 (stable) ships these built in: pydantic 2.12.5, pydantic_core 2.41.5, fastapi 0.136.1, starlette 1.0.0, anyio 4.13.0, httpx 0.28.1, pytest 9.0.2, pytest-asyncio 0.25.3, openai 2.30.0, jiter 0.13.0, sqlalchemy 2.0.48. pydantic-ai is not built in and must be installed with micropip.** [high] _(via Octen (search + extract))_
  Pure-Python wheels from PyPI install with micropip. Pyodide's pydantic (2.12.5) trails upstream: Pydantic v2.14 was announced on 2026-10-08. The browser can only use the single pydantic version Pyodide builds.
  Source: <https://pyodide.org/en/stable/usage/packages-in-pyodide.html>
- **pydantic-ai-slim 2.56.0 (uploaded 2026-10-13) needs Python >=3.11, pydantic>=2.12, anyio>=4.7, httpx2>=2.7, pydantic-graph==2.56.0, opentelemetry-api, genai-prices and griffelib. Its pydantic floor is met by Pyodide's 2.12.5. The 2.56.0 release notes include PR #10134, which fixes `import pydantic_ai.models` on Pyodide. PR #6088 (merged 2026-06-29) runs sync tools and callbacks inline on emscripten because Pyodide cannot start threads.** [high] _(via curl PyPI JSON API (read-only) + gh api (issues #8673 and #6086, PR #6088, release v2.56.0))_
  Issue #8673 states 'Pyodide isn't in CI', so Pyodide support is best-effort and recent. Before #6088, a sync @agent.tool_plain crashed with 'RuntimeError: can't start new thread' on play.pydantic.work, and the workaround was `async def` tools. Pin exact versions if you use the browser.
  Source: <https://github.com/pydantic/pydantic-ai/pull/10134>
- **Standard FastAPI testing with TestClient will almost certainly fail under Pyodide. Pyodide raises RuntimeError on threading, multiprocessing and subprocess. Starlette's TestClient runs through anyio.start_blocking_portal(), which starts a thread. The thread-free alternative is FastAPI's documented async test pattern: httpx.AsyncClient(transport=ASGITransport(app=app)) under pytest.mark.anyio.** [medium] _(via Firecrawl (firecrawl_developer_search: Pyodide FAQ, Starlette testclient.md, anyio discussion #883) + Tavily (FastAPI async-tests docs https://fastapi.tiangolo.com/advanced/async-tests))_
  By the same mechanism pydantic-ai documented in #6086 (anyio.to_thread.run_sync starts a thread), plain `def` FastAPI endpoints and dependencies, which run in a thread pool, are also likely to fail in Pyodide. In-browser FastAPI exercises would therefore need `async def` everywhere plus AsyncClient, which differs from the usual tutorials. This is inferred from the docs and was not run in a browser.
  Source: <https://pyodide.org/en/stable/usage/faq.html>
- **Pyodide memory and load: WebAssembly memory is capped at about 2 GB (32-bit wasm). Pyodide recommends running it in a Web Worker so the page stays responsive. Packages download per browser session from the jsDelivr CDN and are then cached by the browser.** [medium] _(via Octen (search; also https://pyodide.org/en/stable/usage/downloading-and-deploying.html))_
  A one-tab Python runtime is lighter than VS Code plus a local venv, but loading pydantic-ai, httpx2 and opentelemetry costs bandwidth and memory on each cold start. The 2 GB figure comes from a Stack Overflow answer that names the Emscripten 32-bit target.
  Source: <https://stackoverflow.com/questions/75559641/memory-limits-in-pyodide>
- **JupyterLite runs notebooks fully in the browser through jupyterlite-pyodide-kernel (packages installed at runtime with piplite) or xeus-python (packages pre-installed at build time from emscripten-forge), and can be deployed to GitHub Pages.** [medium] _(via Firecrawl (firecrawl_search))_
  It shares Pyodide's thread limits. Its notebook format is not a natural fit for short tasks that are checked automatically. A plain Pyodide Web Worker with a code editor, as play.pydantic.work does, is a better fit for the site.
  Source: <https://jupyterlite.readthedocs.io/en/latest/howto/configure/kernels.html>
- **Pydantic AI's official testing guide gives deterministic, key-free checks for hands-on tasks. TestModel calls every tool and then returns text or structured output. FunctionModel scripts specific tool calls. models.ALLOW_MODEL_REQUESTS=False blocks real model calls. Agent.override swaps model, dependencies or toolsets. capture_run_messages lets a test assert on the message exchange.** [high] _(via Firecrawl (firecrawl_scrape, query format))_
  The docs have moved: ai.pydantic.dev/testing/ redirects to pydantic.dev/docs/ai/guides/testing/. These tools let a hidden test assert things like 'your agent registered a tool named get_weather and returned a WeatherReport', with no API key or network.
  Source: <https://pydantic.dev/docs/ai/guides/testing/>
- **Pydantic AI publishes a single-file docs dump at pydantic.dev/docs/ai/llms-full.txt, which is useful for the scheduled re-sync of the tutor's docs index.** [medium] _(via Firecrawl (firecrawl_developer_search))_
  Seen in a developer-index search hit with page anchors (citation_url ...llms-full.txt#s0). Ingesting one file with stable headings is simpler than crawling, and the docs host itself moved from ai.pydantic.dev to pydantic.dev/docs/ai/. ### Recommendations
- Track 1 (Pydantic AI), main approach: (a) a local practice repo checked with pytest. Ship hidden tests that use TestModel/FunctionModel through Agent.override, with models.ALLOW_MODEL_REQUESTS=False, so checks are deterministic, offline and need no API key. Install only pydantic-ai-slim (no extras) in a uv venv to keep RAM and disk small. Add a small `learn` CLI modelled on Boot.dev and Exercism: `learn pull <lesson>` fetches the stub and tests, `learn check <lesson>` runs pytest, and `learn submit` posts per-test pass/fail plus a hash of the test file to the site API using a personal token.
- Track 1, secondary: (d) a Pyodide 'warm-up' panel inside lessons (Web Worker plus code editor, as on play.pydantic.work) for 1-3 minute micro-tasks such as predicting the output or fixing a model. Pin pydantic-ai-slim to an exact version of at least 2.56.0, use only TestModel or FunctionModel, prefer async tools, and never send real LLM calls from the browser in release 1. If it breaks, fall back to the local CLI. Pre-filled pydantic.run links (GET /new?files=...) are a zero-effort stopgap.
- Track 2 (FastAPI), main approach: (a) the local practice repo with pytest and TestClient, which works normally outside the browser, checked by the same `learn check` CLI. Do not use Pyodide for FastAPI checks in release 1: TestClient needs a thread, and sync endpoints probably do too. Keep the database lessons light on RAM by using a Neon branch (or SQLite for early lessons) instead of local Docker Postgres.
- Track 3 (GitHub), main approach: (b) a GitHub-Skills-style public practice repo built from your own template. Copy the MIT exercise-toolkit pattern: one workflow per step, triggered by real events (push, pull_request, pull_request_review, check failures), with an issue comment holding the results table and `gh workflow enable` to chain steps. The site reads progress with GET /repos/{owner}/{repo}/commits/{ref}/check-runs (plus PR and review endpoints) using a fine-grained PAT scoped to that one repo with read-only Checks, Pull requests, Contents and Metadata, stored as a Vercel environment variable. Keep the repo public: Actions minutes are free and branch protection works on GitHub Free.
- Track 3 extras: link learngitbranching levels (MIT; ?NODEMO&command=... or ?gist_level_id=...) for rebase, branching and remotes before the real-repo task. For the Claude Code + MCP lessons, check what the session leaves in GitHub that a workflow can verify (a PR exists from a named branch, its body has the required sections, CI is green, a review was requested). Grade the parts that only happen locally with (e) paste-your-output plus the LLM rubric.
- Use (e) paste-your-output self-check only where automation is impossible or costly: real-LLM runs (paste the agent output or a Logfire trace link), local Claude Code sessions, and judgement questions such as 'is this PR ready to merge?'. Grade with the LLM rubric and require a specific artefact (command output, URL or SHA) so the answer is grounded.
- Keep (c) Codespaces as an escape hatch, not the default. Add a .devcontainer to each practice repo so one click gives a 2-core/8 GB machine when the Mac is short on RAM. Tell the learner to stop codespaces when finished: Free gives about 60 two-core hours a month, the default idle timeout is 30 minutes, and storage counts against 15 GB-month even while stopped.
- Design the tutor as a visible hint ladder (nudge, concept, cited docs passage, partial code, full answer) with an explicit, logged 'reveal' button. Enforce the current rung in code, not only in the prompt, and keep a small evaluation set of 'please just give me the answer' prompts, as the CS50 and arXiv 2608.12292 lessons suggest. Give the tutor the lesson's task and the learner's latest test failures as context, because context-free Socratic tutors were rated poorly.
- Make lessons feel like play by borrowing proven mechanics: XP and streaks per passed check (Boot.dev), runnable and editable examples inside the reading (Scrimba and pydantic.run), and a live pass/fail table that updates as the CLI or Actions report in (GitHub Skills issue comments).

### Risks
- Pyodide support in pydantic-ai is very new and best-effort. The import fix shipped in 2.56.0 on 2026-10-13, and issue #8673 says Pyodide is not in CI. Any pydantic-ai release could break the in-browser panel. Pydantic AI could also raise its pydantic floor above Pyodide's single built-in 2.12.5, which would break browser runs until Pyodide catches up.
- FastAPI in the browser would force async-only endpoints and AsyncClient tests. That differs from mainstream tutorials and could confuse a learner who wants FastAPI to 'stick'. The TestClient conclusion is inferred from the docs and was not run in a browser.
- A public GitHub practice repo makes the learner's practice commits public. API keys must never be committed (use Actions secrets), and the workflows should not echo secrets. A private repo instead uses Actions minutes (2,000 a month on Free) and loses branch protection unless the learner has GitHub Pro.
- Self-checks are trivially fakeable: a learner can edit the test files or workflow files, and CLI submissions are self-reported. That is acceptable for a solo owner in release 1, but before paid accounts, grading must move to server-side or Actions-side runs against protected copies of the tests (e.g. compare the workflow-file hash or use a required check the learner cannot edit).
- Chained workflows (`gh workflow enable` per step) are fragile. A failed step, a renamed branch or an edited workflow can leave the exercise stuck, and GitHub Skills tells users to check the Actions tab and file an issue. The site needs a 'reset this step' path.
- Codespaces quota: leaving a codespace running until the idle timeout, or keeping several stopped codespaces, eats the 120 core-hours and 15 GB-month. Usage beyond the quota is billed if a payment method or budget allows it.
- Tutor design risk: prompt-only guardrails leak answers (CS50), while strict Socratic tutors frustrate learners and drive them to general chatbots (arXiv 2609.29995, 2504.11146). Getting this balance wrong could make the site feel like a chore.
- Tool coverage: Tavily failed partway through the session (HTTP 429 rate limit on extract, then 432 plan usage limit on search). Some later claims (check-runs docs, Boot.dev's Boots, Pyodide memory) rest on Octen, Firecrawl and gh api only.
- pydantic.run's repo has not been pushed since 2025-04-08, and play.pydantic.work is a public Pydantic service. Linking to either creates a dependency on infrastructure you don't control, so self-host the Pyodide runner for anything core.
